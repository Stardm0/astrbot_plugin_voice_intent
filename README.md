# 开口吧 · astrbot_plugin_voice_intent

> 随口一句「用语音跟我说」「念给我听」「别打字了」，机器人这一轮就用语音回你。
> 没这个意思时，一个字都不动 —— 默认人格、陪伴插件、分段、表情、核心概率 TTS 全部照旧。
> 另补上**模型感知层**：AI 知道自己这一轮是说出来的，也记得上一轮发的是语音。

---

## 一、它解决的到底是哪件事

AstrBot 里「文本转语音」和「让 AI 发一条语音」是两条互不相干的路：

| 路径 | 谁触发 | 问题 |
| --- | --- | --- |
| 核心自动 TTS | 框架在 `ResultDecorateStage` 按 `tts_trigger_probability` 掷骰子，把纯文本结果换成 `Record` 语音段 | 只能概率，不能「我说一句就发」 |
| LLM 工具（第三方插件的 `text_to_sound` / `tts_speak`） | 模型自己决定调工具 | 会话没启用 TTS、人格工具白名单没勾、工具名改过没重新启用，就会报「**工具没接上**」 |
| 手动指令（`/tts_say`、`/合成`、`vits_say`） | 你敲命令 | 得装插件，而且大多自带另一套 TTS 引擎 |

本插件走的是**第三条之外的路**：既不给模型注册工具，也不另起 TTS 引擎，而是挂在
`@filter.on_decorating_result()` 上——官方文档说这个钩子「可以在这里实现一些消息的装饰，
比如**转语音**、转图片、加前缀等等」。

于是链路变成：

```
用户说「用语音跟我说句晚安」
  ↓ 插件只读用户这一轮的原话，判「有没有想听语音的意思」
  ↓ 命中 → 把 LLM 本轮回复的纯文本抽出来、清洗
  ↓ 交给 AstrBot 当前已配置好的 TTS Provider（context.tts / curr_tts_provider_inst.get_audio）
  ↓ result.chain 换成 [Record, ...]
  ↓ 发送
未命中 → 函数直接 return，链路零改动
```

**所以不会有「工具没接上」**：模型全程不知道自己在发语音，它只是正常生成了文本回复，
插件在发送前把媒介换掉了。也不会「绕开已调好的音色」——见第五节。

## 二、安装与三个前置

1. 把 `astrbot_plugin_voice_intent/` 整个目录放进实例的 `data/plugins/`
   （Launcher 可视化版点实例行的文件夹图标最直接）
2. WebUI → 插件管理 → **重载插件**
3. 发 `/开口 自检`，应返回「结论：全部就绪 ✅」

### ⚠️ 三个前置，缺一个就会「配了没反应」

| # | 前置 | 为什么 |
| --- | --- | --- |
| 1 | **关闭 AstrBot 的流式输出** | `ResultDecorateStage` 对 `STREAMING_RESULT` **整体跳过**，连 `on_decorating_result` 钩子都不广播。官方 issue 里维护者也确认「流式输出时 tts 不生效」 |
| 2 | WebUI → 模型提供商 → 文字转语音 → 点「**测试**」能出音频 | 插件调的就是这个 provider，它不通，插件只会保留原文本并在日志写一行错 |
| 3 | 两个改动过的 core 补丁还在 | 见第五节：Launcher 升级会整体替换 core + 重建 venv，`dashscope_tts.py` 的两个补丁会被覆盖 |

> 核心自带的概率 TTS **不用关、也不用改**。插件只是在「命中意图的那一轮」强制语音，
> 没命中的轮次仍由核心按原概率决定。两者叠加而非互斥。

## 三、怎么用

### 自然语言（不需要任何指令）

```
用语音跟我说句晚安           → 这一句用语音
发条语音告诉我明天几点       → 这一句用语音
念给我听                    → 这一句用语音
不想看字了，你直接讲吧       → llm 档能抓，这一句用语音
以后都用语音回我吧           → 接下来都用语音，直到你说停
还是打字吧 / 别发语音了      → 改回文字
```

**两种作用域**，判定器自己分：

- `once`：只这一轮（「用语音说句晚安」）
- `session`：接下来都用语音（「以后都用语音」「别打字了」）。之后每轮**不再调判定器**，
  直接强制语音，所以长期模式几乎不增加成本。说「还是打字吧」或发 `/开口 关` 结束。
- **拿不准一律 `once`**，绝不擅自切成长期模式。

### 手动触发语音（不靠自然语言，也不靠工具）

```
/开口 发 今晚早点睡              → 直接把这句合成一条语音发出来
/voice say 晚安                  → 同上
/开口 说：周末见                  → 同上（冒号可紧贴）
/开口 念 别熬夜了 /开口 朗读 明天见 /voice speak, hello → 同上
```

- **不走 LLM、零模型调用**：文本由你指定，插件直接调当前已配好的 TTS Provider 合成并发出
- **别名**：`发` / `说` / `念` / `读` / `朗读` / `念一句` / `来一句` / `say` / `speak` / `voice` / `tts`
- **空内容、全是表情标记、超过朗读上限、合成失败**：都会给一句明确文字说明，绝不静默丢消息
- 若 `attach_text=true`，会同时附一份原文（显示用，留给 `face_convert`）
- 这条语音会以 `by=command` 登记进感知层，下一轮回执明确告诉模型「内容不是你生成的」，
  不会把用户指定念的话误认成自己说过（见第七节）

### 指令一览（`/开口` 或 `/voice`，两套前缀完全等价）

| 指令 | 别名 / 参数 | 作用 |
| --- | --- | --- |
| **`/开口 发 <内容>`** | `说` `念` `读` `朗读` `say` `speak` `voice` `tts` | **手动发一条语音**，不调 LLM |
| `/开口` | `/voice` | 状态总览（判定档位、语音模式、附原文、字数上限、感知、上一轮实况） |
| `/开口 状态` | `检查` `status` `check` | 同上 |
| `/开口 开` | `on` `开启` | 进入「接下来都用语音」 |
| `/开口 关` | `off` `关闭` `停` `stop` | 改回打字 |
| `/开口 一次` | `once` `这轮` | 只**下一句**用语音（预约，不是本轮） |
| `/开口 判定 <档位>` | `mode` `档位`；`keyword` / `llm` / `always` | 在线切判定档位；不带参数显示当前档位与说明 |
| `/开口 感知` | `aware` `记性` | 看模型记不记得自己上一轮用语音回过 |
| **`/开口 校验`** | `verify` `验指令` `检查指令` | **逐条校验所有指令解析**，零模型 / 零发送 / 零状态改动 |
| `/开口 自检` | `selftest` | 静态自查钩子与 TTS Provider 是否就绪，不调模型、不计费 |
| `/开口 清` | `reset` `清空` | 清空语音模式、一次性标记、档位覆盖与上一轮实况 |
| `/开口 帮助` | `help` `指令` `commands` | 运行时打印本清单 |

> 少数 AstrBot 版本对多个 `@filter.command` 只认一个（且中文指令名不一定注册成功）。
> 若 `/开口` 没反应，改用 `/voice`；反之亦然。指令解析兼容完整原文、框架只给参数、
> 全角斜杠、零宽字符、`@某人` 前缀、head 后紧跟 `:` `：` `,` `，` 且无空格。

### 指令校验：解析层 + 生效层

**运行时**：发 `/开口 校验`，逐条跑 `COMMAND_MATRIX` 的解析，输出 `N/N 通过`、
别名数、已注册分支数，异常会列出具体哪条被解析成了什么。纯静态，不改任何状态。

**离线（真正验证「生效」）**：

```powershell
cd <实例>\data\plugins\astrbot_plugin_voice_intent
.venv\Scripts\python.exe _selftest.py
# 最后一行应为：结果：全部通过 OK（227 项）
```

自检对 `COMMAND_MATRIX` 里**每一条**都用全新插件实跑 `cmd_admin`，断言：
非管理指令不返回「没认出参数」；`开/关/一次/判定/清` 的状态副作用确实发生；
手动指令的所有别名都真的合成出 `Record` 并被 `chain_result` yield 出去；
空内容 / 超长 / 合成失败各有明确回话且不登记语音实况；帮助清单与 README 都列全了这些指令。
`COMMAND_MATRIX` 是 `main.py` 里的单一数据源，运行时校验、离线自检和本节清单三处共用，
避免出现「文档写了一条、代码其实不认」。

## 四、三档判定与成本

| 档位 | 怎么判 | 成本 | 适合 |
| --- | --- | --- | --- |
| **`keyword`（默认，推荐）** | 内置关键词表 + 可选自定义正则，命中即开口 | **零模型调用** | 绝大多数场景 |
| `llm` | 先用宽松闸门召回（关键词、隐含线索如「懒得看」「耳朵」「不…打字」，以及关闭词），再让模型读语义输出 JSON | 只在闸门召回时 1 次 | 想抓「不想看字了」这种没提「语音」二字的话 |
| `always` | 每句都判 | 每轮 1 次 | 调试用，不建议长期 |

**闸门的三条硬规则**（三档都遵守）：空消息、斜杠指令、去掉表情标点后不足 `min_chars`、
纯表情 → 一律零调用放行。所以**不会「每句都判导致没法闲聊」**。

`llm` 档的判定提示词里专门压了一条：

> 他让你「说晚安」「讲个故事」「跟我聊聊」这类**只是要内容**的话不算，那是普通聊天，
> 判 `want=false`。别把「说」字一律当成要语音。

并明确「拿不准就 `want=false`」「判定失败一律放行」——宁可少发一条语音，绝不改坏回复。

⚠️ **`keyword` 档的已知局限**：用户问「你会发语音吗」也会因为含「发语音」而触发。
想避免就切 `/开口 判定 llm`，模型会把「在聊功能本身」判成 `want=false`。

配置 `judge_provider_id` 建议填一个便宜快模型：判定只输出一小段 JSON。

## 五、为什么能复用你已经调好的百炼音色

这是这个插件最要紧的设计点。它**不引入任何新 TTS 引擎**，`_synthesize()` 依次尝试：

```python
# 路径 1
self.context.tts(text)
# 路径 2（优先使用，正是核心 ResultDecorateStage 用的那个实例）
self.context.provider_manager.curr_tts_provider_inst.get_audio(text)
```

`curr_tts_provider_inst` 就是 WebUI 里「文字转语音」选中的那个 provider 实例。所以：

- `dashscope_tts.py` 的**路由补丁 A**（让 `qwen-audio` 走 `tts_v2` WebSocket 而非 HTTP 多模态）生效
- **接线补丁 B**（`dashscope_instruction` / `dashscope_speech_rate` / `dashscope_pitch_rate`）生效
- `cmd_config.json` 里那三行（指令留空、语速 **1.04**、音高 1.0）生效
- 复刻音色 `qwen-audio-3.1-tts-flash-bailian-699` 生效

换成第三方 TTS 插件才会绕开这些——那些插件大多自带 siliconflow / minimax / 火山 ICL
引擎，等于音色、语速、调音全部重来，还得关掉内置 TTS 避免二次合成。

**返回值归一化**做了兼容：bytes、base64 字符串、`data:audio/...;base64,`、文件路径、
dict、带 `.audio` 的对象都能吃；最后构造 `Comp.Record(base64=...)`，若你的版本不支持
`base64=` 参数，会自动写临时文件退回 `Comp.Record(file=..., url=...)`。

## 六、和你链路上其它东西的关系

| 邻居 | 关系 |
| --- | --- |
| **陪伴插件 / 人格 / 日程注入** | 完全不碰。插件只装饰**发送前的结果链**，不改 `system_prompt`、不 `stop_event`、不注册工具 |
| **核心概率 TTS** | 叠加，不互斥。插件先检查链里是否已有 `Record`，有就跳过，绝不二次合成 |
| **分段发送** | 命中语音时整条回复变成一条 `Record`，核心/陪伴插件的分段看到没有可切的文本段，自然不切成多条 —— 正好是「一条语音」，不会出现前面担心的「每段独立合成、语音条翻倍」 |
| **`face_convert` / `[旺柴]`** | 送 TTS 前按踩坑 #14 删掉 `\[[A-Za-z一-鿿]{1,6}\]` 表情标记，避免把「旺柴」念出来。**只改合成文本**；开 `attach_text` 时附的原文保持原样，留给下游转真 QQ 表情 |
| **`[NO_REPLY]` 静默暗号** | 默认整条跳过不合成（`skip_tokens` 可配） |
| **超长回复** | 超过 `max_tts_chars`（默认 500）保留文字不发语音，避免一条超长语音 + 白花 token |
| **合成失败** | 明确记一行 error，**保留原文本回复**，绝不静默丢消息或发一条空语音 |
| **TTS Provider 未配置** | `/开口 自检` 会显示 ✗；运行时只保留文本并给出明确报错 |

⚠️ `attach_text=true` 时会在语音后附一条纯文本，核心概率 TTS 若不为 0，可能对这条文本
二次合成。开这项建议把核心 `tts_trigger_probability` 设为 0。

## 七、模型感知层：AI 怎么会知道自己刚才「说了话」

### 问题真的存在

v1.0 是**纯装饰层**：模型只生成了文本，插件在发送前把 `chain` 换成 `Record`。
于是模型的历史里自己「打了一段字」，用户耳边却是一段声音。下一轮就会出现：

| 用户说 | 模型（不知道时） |
| --- | --- |
| 「你刚才那条语音再说一遍」 | 「我刚才没发语音呀 / 你说的是哪段文字？」 |
| 「别念了，太长了」 | 「我上一条是文字，不长啊」 |
| 「你刚说的第二句是什么意思」 | 引用自己历史里那段**文本**，可用户听到的版本被删过表情标记，对不上 |

这不是 bug，是「不侵入模型」的代价。**而且不管语音是谁发的都一样**：本插件不注册任何
LLM 工具，所以严格说没有「调用工具」这一步；但如果你那边另有工具型 TTS 插件，模型
同样可能只拿到一个「已发送」返回值却没有把它变成自我认知。下面这套机制和语音由谁
发出无关，只依赖「有没有真的发出去」。

### 三层补齐，全程零模型调用

**① 生成之前就告知（本轮）** —— `@filter.on_llm_request()`，命中语音意图时往
`req.system_prompt` 追加一小段：

> 你这一轮的回复会被直接转成**语音**朗读给用户，他听到的是声音，不是文字。
> 请按「说给人听」来写：短句、口语、别用 markdown / 代码块 / 表格 / 括号注释 /
> 长列表 / 只有看字才懂的排版。……心里记住：这一轮你是**说**出来的，不是打出来的。

这一步顺带解决一个更实际的问题：模型不再写出适合阅读、念出来却很怪的文本。
`session` 持续模式下每轮都注入一段更短的「你一直在用语音说话」，避免它写回长文。

**② 下一轮回执（上一轮）** —— 只有**真的发出语音**才登记 `last_voice`，下一轮请求前注入：

> 你上一条回复是以**语音**发给用户的，不是打字。……朗读出来的内容大致是「…」。
> 别以为自己刚才打了字，也别说「上面那段文字」「我刚才写的」。
> 他若提到「刚才那条语音 / 你刚念的 / 再说一遍」，指的就是这一条。

三个细节：
- 存的是**实际朗读版本**（`_clean_for_tts` 删过 `[旺柴]` 之后的内容），不是模型原文，认知才对得上
- `attach_text=true` 时会如实说明「语音和文字都收到了」，不会让模型以为只有语音
- 只注入**紧接着的下一轮一次**（`injected` 标记），不每轮念经；默认 30 分钟 TTL

**③ 登记必须诚实** —— 合成失败、超长保留文字、静默暗号、`[NO_REPLY]`，**一律不登记**。
让模型「以为自己说了话」比不知道更糟。说「还是打字吧」时会主动清掉实况。
另外登记带 `by` 来源：`by=model` 回执是「你上一条回复是以语音发的」；
`by=command`（`/开口 发 <内容>` 直接念的）则改成「刚才由指令直接发了一条语音，
内容不是你生成的」，避免模型把用户指定念的话认成自己说过。

### 为什么不写进数据库

AstrBot 的会话历史里那条 assistant 消息仍然是**文本**。我们没有去改它：

- 改历史会污染陪伴插件 / 人格 / 长期记忆读到的同一份上下文，风险远大于收益
- 不同版本的 `conversation_manager` API 差异大，写错会直接丢会话
- 下一轮回执已经覆盖主要场景（「刚才那条语音」几乎都发生在紧接着的下一轮）

**诚实边界**：如果用户隔了十几轮再问「你上周那条语音说了啥」，模型查不到 —— 它的
历史里确实只有文字。要彻底解决，得在 `on_decorating_result` 里用
`context.conversation_manager` 追加一条 system note 到该会话历史（并把这条 note 标成
`_no_save` 之外可持久、但默认不喂给模型全文）。这条留给你按需做，README 第七节的
版本核对命令可以顺手确认 API 名；本插件默认不碰历史。

### 三个配置项

| 键 | 默认 | 作用 |
| --- | --- | --- |
| `in_request_aware` | `true` | 感知层总开关。关掉 = 回到 v1.0 纯装饰，语音照发但模型不知道 |
| `receipt_ttl_minutes` | `30` | 上一轮实况保留多久，超期不再注入回执 |
| `aware_extra` | 空 | 追加一句自定义要求（如「称呼要带姓氏」） |

### 和叠加注入的关系

你实例上陪伴插件、`schedule_awareness`、心境中枢都在往同一个 `system_prompt` 追加。
本插件只加**一小段**、放在末尾、带 `[[voice_intent_aware]]` 去重标记：同一轮工具循环里
多次 LLM 请求复用同一个 `req` 时不会重复追加。`on_llm_request` **全程不调模型**
（keyword 档判定零调用；llm/always 档只给一句温和的「回复可能被朗读，写成口语短句」，
精确判定仍留在 `on_decorating_result`），所以不会出现「正准备发请求又嵌套调一次模型」。

降级路径：`req` 没有 `system_prompt`、或感知层关闭、或前置 hook 没注册成功 —— 前置
直接 return，`on_decorating_result` 会自己补判并照常发语音，**功能一点不丢**，只是模型
又不知道了。

发 `/开口 感知` 可以看当前有没有登记上一轮实况、回执注入过没有；`/开口 自检` 会列出
`on_llm_request` 与 `_note_voice` 两项是否就绪。

## 八、`/开口 校验` 回「没认出参数」怎么排

实测（QQ 聊天截图）：连发三次 `/开口 校验`，机器人每次回三条——
「没认出参数」「「[主人(2581793700)]」」「发 /开口，帮助，看清单。」

**中间那条是决定性证据。** 兜底文案是 `没认出参数「{head}」…`（被陪伴插件的分段
切成了三条），所以 `head` 被解析成了 `[主人(2581793700)]` —— 这是 QQ 的 **At 组件
显示文本**，被框架或陪伴插件拼进了 `message_str`。旧版 `_clean_input` 只剥
`[CQ:at,...]` 和 `@前缀`，不认 `[主人(QQ号)]`，于是 At 文本被当成指令名，
真正的 `校验` 反而没被读到。

### 按顺序排，别一上来改代码

**① 先确认跑的是新包（最常见、最省事）**

发 `/开口 帮助`：
- 清单里有 **`/开口 校验`** 和 **`/开口 发 <内容>`** → 新包已加载，跳到 ②
- 没有这两行 → **实例上还是旧版**。覆盖目录后必须在 WebUI **重载插件**，
  并确认覆盖的是 **Launcher 实例的 `data/plugins/`**（可视化版点实例行的文件夹图标），
  不是项目根 `.venv` 旁边那份。改了文件不重载，运行中仍是旧类

**② 新包仍报错 → 看兜底那行 `[诊断]`**

新包在「没认出参数」后面会附一行 `[诊断] 清洗后原文：…`。把它贴出来就能看出
框架到底把指令切成了什么样。

**③ 已内置的容错（不用你动手）**

| 形态 | 处理 |
| --- | --- |
| `[主人(2581793700)]/开口 校验`、`/开口 校验[主人(...)]` | 清洗时**全局**删掉方括号 At 段，不只剥前缀 |
| `[CQ:at,qq=…]`、`[@昵称]`、`<at>…</at>`、`@机器人(QQ)` | 同上；多个前缀循环剥 |
| `message_str` 只剩 At 文本 | 从 `message_obj.message` 里把所有 `Plain` 段拼回来（跳过 At/图片/语音），选能解析出已知指令的那一份 |
| 解析出的 head 仍不认识，但原文含「校验/帮助/自检/…」 | 关键字兜底，按那条指令执行，不掉进兜底 |
| `[旺柴]` 这类表情标记 | **刻意不删**（没有「括号 + 5~12 位数字」），留给 `face_convert` |

**④ 另一个老提醒**：两个 `@filter.command`（`/开口` 与 `/voice`）在少数版本只认一个。
`/开口` 没反应就换 `/voice 校验`；反之亦然。

> 顺带说明截图里「回复被切成三条」：那是陪伴插件智能分段 + 核心分段叠加的效果
> （见前面几轮的讨论），不是本插件发的三条消息。核心分段必须开着，插件那层才生效。

## 九、版本核对清单（装之前花 30 秒）

不同 AstrBot 版本的 API 名略有差异。在**实例的 AstrBot core 目录**里跑：

```powershell
$core = "<实例>\astrbot\core"

# 1) 两个装饰器钩子是否存在、签名是什么（顺带核 req.system_prompt 可写）
Select-String -Path "$core\pipeline\result_decorate\stage.py" `
  -Pattern 'on_decorating_result|on_llm_request|tts_trigger_probability|STREAMING_RESULT|get_audio|Record\(' |
  % { '{0,4}: {1}' -f $_.LineNumber, $_.Line.Trim() }

# 2) TTS Provider 实例与抽象方法名
Select-String -Path "$core\provider\manager.py","$core\provider\provider.py" `
  -Pattern 'curr_tts_provider_inst|def get_audio|class TTSProvider' |
  % { '{0}:{1}: {2}' -f (Split-Path $_.Path -Leaf), $_.LineNumber, $_.Line.Trim() }

# 3) Record 支持哪些参数
Select-String -Path "$core\message\components.py" `
  -Pattern 'class Record|def __init__|base64|file' -Context 0,12 |
  Select-Object -First 40

# 4) context 上有没有 llm_generate / get_current_chat_provider_id / tts
Select-String -Path "$core\star\context.py","$core\star\star.py" -Recurse -ErrorAction SilentlyContinue `
  -Pattern 'def llm_generate|def get_current_chat_provider_id|def tts' |
  % { '{0}:{1}: {2}' -f (Split-Path $_.Path -Leaf), $_.LineNumber, $_.Line.Trim() }
```

| 核对结果 | 要改什么 |
| --- | --- |
| `on_decorating_result` 不存在 | 版本过旧，升到 ≥ 4.5.7 |
| `get_audio` 叫别的名 | `main.py` 的 `_synthesize()` 里那个 `for name in (...)` 元组加上实际名 |
| `Record(base64=)` 抛 TypeError | 已内置自动退到 `file=`，不用改；若仍失败，照第 3 条输出改 `_make_record()` |
| 没有 `context.llm_generate` | `llm` / `always` 档不可用，保持默认 `keyword` 档（零模型调用，完全不受影响） |
| `on_llm_request` 签名不是 `(event, req)`，或 `req` 无 `system_prompt` | 感知层自动降级：语音照发，模型不知道。按实际签名改 `on_llm_request` 形参即可 |
| 核心构造 Record 的方式和本插件不同 | 照第 1 条里 `Record(` 那行改 `_make_record()` 一行 |

> 这些 API 名按公开文档与当前主干写，但没拿到你实例源码原文，请现场核一遍再上。

## 十、已知边界

- **只判用户这一轮的原话**，不读历史。所以「接着刚才那样」这种依赖上下文的省略说法判不出来；
  长期模式请用 `/开口 开` 或明确说「以后都用语音」。
- 只处理 `chain` 里的纯文本 `Plain`；图片、`@` 等非 Plain 组件会保留在语音后面。
- 回复本身已是 `Record`（核心概率先命中了）时插件跳过，不二次合成。
- 状态落在 `data/plugin_data/astrbot_plugin_voice_intent/voice_state.json`，只存
  「哪个会话在用语音模式 + 一次性标记 + 档位覆盖」，**不存任何聊天内容**。
- 只做被动回复装饰，**不处理主动消息**、不注册 LLM 工具、不改会话配置。
- **不改持久化对话历史**：历史里那条 assistant 消息仍是文本，靠下一轮回执修正当下认知（见第七节）。
- `qq_official` 适配器对语音段支持有限；本插件只在 NapCat / aiocqhttp（6199 那条）实测过。
- 每次命中会多一次 TTS 合成（按你 provider 的计费口径），`max_tts_chars` 就是给这个兜底的。
